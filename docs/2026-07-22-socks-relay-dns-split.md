# Спецификация: DNS-split и direct-net в SOCKS-реле

**Дата:** 2026-07-22
**Статус:** спецификация (до реализации)
**Файлы:** `../socks/socks-relay.py`, новый `../socks/dns_split.py`, `../socks/test_socks_relay.py`, `./start.sh`

---

## 1. Зачем это нужно (постановка задачи человеческим языком)

### 1.1. Топология

У нас есть три участника:

1. **Контейнер** (devbox) — в нём поднят `sing-box`, который создаёт виртуальную
   сетевую карту `tun0` и заворачивает в неё **весь** трафик контейнера (режим
   `hostproxy`). Из `tun0` трафик уходит в SOCKS5-реле на хосте.
2. **Реле** (`socks-relay.py`) — работает **на хосте**, принимает трафик из
   контейнера. Запущено в режиме **цепочки** (chained): у него задан вышестоящий
   SOCKS5-прокси (`SOCKS5_SERVER`), и весь трафик реле по умолчанию отправляет
   туда — во **внешний VPN** пользователя (тот, что обходит блокировки ТСПУ).
   Флаг `-I <iface>` жёстко привязывает исходящие соединения реле к внешнему
   интерфейсу (как `curl --interface`).
3. **Хост** — на нём периодически поднимается корпоративный VPN (Cisco
   AnyConnect). Когда он поднят, хост видит корпоративную сеть: внутренние
   подсети `10.0.0.0/8` и внутренний DNS-сервер `10.50.50.50`. Когда VPN
   выключен — этой сети нет, а `10.50.50.50` недостижим.

```
┌─────────────┐   tun0    ┌──────────────┐  upstream SOCKS  ┌──────────────┐
│  Контейнер  │ ────────► │     Реле     │ ───────────────► │ Внешний VPN  │
│  (sing-box) │  всё сюда │  (на хосте)  │   (обход ТСПУ)   │  (интернет)  │
└─────────────┘           └──────┬───────┘                  └──────────────┘
                                 │ direct (в обход upstream, по таблице хоста)
                                 ▼
                          ┌──────────────┐
                          │ Корп-сеть    │  10.0.0.0/8, DNS 10.50.50.50
                          │ (через VPN   │  доступна ТОЛЬКО когда
                          │  хоста)      │  AnyConnect поднят
                          └──────────────┘
```

### 1.2. Проблема

Сейчас реле отправляет **всё** во внешний VPN (upstream), привязывая к внешнему
интерфейсу `-I`. Из-за этого:

- **Корпоративные адреса `10.0.0.0/8` недостижимы** из контейнера: запрос к ним
  улетает во внешнюю трубу, а не в корпоративную сеть хоста.
- **Внутренний DNS `10.50.50.50` недостижим** по той же причине — а значит
  корпоративные доменные имена (`*.corp.example`) не резолвятся.

### 1.3. Чего хотим

1. Трафик к корпоративным подсетям (`10.0.0.0/8` и т.п.) должен идти **напрямую
   по таблице маршрутизации хоста** — в обход и внешнего VPN (upstream), и `-I`.
   Тогда хост сам дотянется до корп-сети (через свой AnyConnect), когда тот
   поднят.
2. **DNS должен резолвиться правильно в обоих состояниях VPN**, при этом:
   - контейнер **не должен** знать адрес корп-DNS (`10.50.50.50`) — он меняется и
     зависит от того, поднят ли VPN;
   - контейнер **не перезапускается** — нельзя «зашить» DNS один раз при старте;
   - корпоративные имена → резолвятся корп-DNS (когда VPN поднят);
   - обычные интернет-имена → резолвятся внешним DNS и **не тащатся** в
     корпоративный/внешний VPN без нужды.

## 2. Почему именно такая схема (разбор альтернатив, которые мы отвергли)

По ходу проектирования мы разобрали и отбросили несколько вариантов. Фиксируем
причины, чтобы к ним не возвращаться.

### 2.1. Почему нельзя «зашить» DNS-адрес в контейнер

Если прописать контейнеру DNS = `10.50.50.50`, то когда VPN на хосте **выключен**,
этот адрес мёртв. `sing-box` версии 1.13.14 **не умеет** DNS-фолбэк между
серверами: мёртвый основной сервер приводит к зависанию запроса на ~10 секунд, а
затем к ошибке — без автоматического перехода на запасной. (Проверено запуском
самого бинаря: поля `fallback`/множественный `address`/`servers` не
поддерживаются; `dns.timeout` появился только в 1.14; профильные issue в
апстриме отклонены.) Значит фиксированный корп-DNS в контейнере ломает резолвинг
всякий раз, когда VPN выключен.

### 2.2. Почему нельзя «реле резолвит через getaddrinfo хоста» в лоб

Идея: контейнер отдаёт реле **имя** (SOCKS ATYP=DOMAIN), а реле резолвит его
через системный резолвер хоста (`getaddrinfo`), который сам следует за VPN.

**Отвергнуто** по возражению пользователя: если реле резолвит через дефолт хоста
**без `-I`**, а VPN хоста поднят, то `getaddrinfo` пойдёт по системной таблице
маршрутизации → **все** имена, включая `google.com`, начнут резолвиться через
корпоративный VPN. Это неверно: обычные интернет-домены не должны тащиться в
корп-сеть.

### 2.3. Почему решаем DNS в реле, а не в sing-box

`sing-box` 1.13.14 не даёт нужной логики (см. 2.1). Реле — единственное место,
которое одновременно: (а) видит адрес назначения каждого соединения; (б) стоит на
хосте, где известно состояние VPN; (в) может принять решение по каждому DNS-ответу
индивидуально. Поэтому DNS-логика живёт в реле.

### 2.4. Почему `--direct-net` нужен в любом случае

Даже если DNS резолвится идеально и возвращает корпоративный `10.x`, **последующее
соединение** к этому `10.x` тоже должно идти напрямую по таблице хоста, а не в
внешний VPN. За это отвечает `--direct-net` — отдельный механизм от DNS-логики.
DNS-split и `--direct-net` **дополняют** друг друга: первый обеспечивает правильный
резолв, второй — правильный маршрут данных.

## 3. Как это работает после реализации (целевая схема)

### 3.1. Ключевой факт: реле маршрутизирует по IP-адресу назначения

`sing-box` отдаёт реле каждое соединение с **уже указанным адресом назначения** в
SOCKS-запросе. Реле не занимается резолвом для маршрутизации данных — оно смотрит
на IP цели и сравнивает с маской `--direct-net`:

- цель ∈ `direct-net` → **прямой** `connect()` по таблице маршрутизации хоста, в
  обход upstream и в обход `-I`;
- иначе → как сейчас: через upstream, с привязкой к `-I`.

### 3.2. Как sing-box шлёт DNS (проверенный факт)

В конфиге контейнера DNS-сервер имеет `type: tcp`, `server_port: 53`,
`detour: proxy`. Цепочка внутри sing-box: `hijack-dns` (route-правило на port 53 /
protocol dns) перехватывает DNS на уровне TUN и направляет его во **внутренний
DNS-резолвер** sing-box; тот, поскольку сервер имеет `detour: proxy`, устанавливает
**TCP-соединение через outbound `proxy` (реле)** на `<dns_server>:53`. Внутри
TCP-потока — DNS-сообщение с 2-байтовым префиксом длины (RFC 7766). Реле
распознаёт DNS по **порту назначения 53**.

> ВАЖНО: реле распознаёт DNS **по порту 53** (константа `DNS_PORT`), а не по адресу
> реле и не по разбору «моё/не моё». Особой логикой обрабатывается TCP-соединение на
> порт 53 **при выполнении всех трёх условий** (см. §5.3): режим `--dns-split`
> активен, задан `-I`, и адрес назначения — **IP-литерал** (ATYP=IPv4; для
> ATYP=DOMAIN — обычный путь реле). Иначе — обычный путь.

### 3.3. Особый режим DNS (флаг `--dns-split`)

Это **не** «гонка на скорость», а **особая логика выбора ответа по маске**.
Активируется флагом `--dns-split` (env `DNS_SPLIT`), который заодно задаёт источник
дефолтного DNS (см. §3.3.2). Когда флаг не задан — DNS обрабатывается как обычный
трафик (всё в `-I`/upstream), логика реле не меняется.

> **Предусловие `-I` (важно):** DNS-развилка имеет смысл только когда задан `-I`
> (внешний интерфейс, который «уводит» трафик от внутренней сети). **Без `-I`
> развилка не активна** — DNS на порт 53 идёт **существующим путём реле** (в
> chained-режиме — через upstream SOCKS; иначе — прямым connect), как любой другой
> трафик. То есть `--dns-split` без `-I` = no-op (реле логирует это при старте).
> Причина: без `-I` внешний и дефолтный пути совпали бы (одна таблица хоста) —
> разделять нечего.

> Включение и значение (полный разбор — §3.3.2). Кратко:
> - **CLI**: `--dns-split` присутствует → включено, значение (`const=''` без
>   аргумента, либо явное) трактуется по §3.3.2. `--dns-split 0`/`false`/`no`/`off`
>   → **выключено** (позволяет CLI перекрыть env `DNS_SPLIT=1`).
> - **env**: `DNS_SPLIT` **непусто** и ≠ `0`/`false`/`no`/`off` → включено; значение
>   как источник. **Пустая строка / не задано → выключено** (согласуется с §4.1:
>   пустой env = «не задано»).
>
> Различие: для CLI флаг-без-значения (`const=''`) — это «включить, системный
> resolv.conf»; для env пустая строка — «не задано, выключено». Общий разбор
> значения (§3.3.2) применяется только к **непустым** значениям.

Когда `--dns-split` включён и пришло TCP-соединение на порт 53:

1. Реле сразу отдаёт клиенту (sing-box) SOCKS-ответ «успех» — иначе sing-box не
   начнёт слать DNS-данные.
2. Реле входит в **цикл чтения** по этому TCP-соединению (одно соединение может
   нести несколько DNS-запросов подряд — pipelining/keep-alive, RFC 7766):
   читает 2-байтовый префикс длины, затем DNS-сообщение, обрабатывает, пишет ответ
   с 2-байтовым префиксом. Цикл до закрытия соединения клиентом.
3. Для каждого запроса: разбирает его через `dnspython`, извлекает имя/тип.
4. Смотрит кэш (см. 3.4). При попадании — возвращает кэшированный ответ.
5. Отправляет **два** параллельных DNS-запроса с таймаутом **2 секунды** каждый
   (транспорт и адреса — см. 3.3.1):
   - **внешний** путь — через интерфейс `-I` на адрес DNS из самого SOCKS-запроса
     (`__DNS_SERVER__` контейнера);
   - **дефолтный** путь — по таблице маршрутизации хоста, **без** `-I`, на DNS из
     системного `/etc/resolv.conf` хоста (когда VPN поднят — это корп-DNS).
6. Выбор ответа **по маске `--direct-net`** (не по скорости):

   | Ситуация | Что возвращаем |
   |---|---|
   | Оба ответили, в ответе **дефолтного** пути есть хотя бы один адрес ∈ `direct-net` | **дефолтный** (внутренний) — ВСЕГДА |
   | Оба ответили, в ответе дефолтного **нет** адресов ∈ `direct-net` (в т.ч. NXDOMAIN, SERVFAIL, не-адресный тип) | **внешний** — ВСЕГДА |
   | Ответил только один (второй молчит > 2 сек) | тот, кто **ответил** |
   | Оба молчат > 2 сек | SERVFAIL с **тем же Query ID**, что в запросе (пусть sing-box повторит) |

   «Ответил» = пришёл любой валидный DNS-ответ (включая NXDOMAIN/SERVFAIL). Если
   исходный запрос не удалось распарсить (обрезанный пакет) **или** в нём не ровно
   одна question-секция (нормальный DNS-запрос несёт ровно одну; ≠1 — аномалия,
   ключ кэша не построить) — соединение закрывается (корректный SERVFAIL под
   неизвестный Query ID/вопрос не собрать).

7. Выбранный ответ кэшируется и возвращается контейнеру.

> Почему выбор именно «дефолтный ∈ direct-net → внутренний, иначе → внешний»:
> маска `--direct-net` — **единый источник правды**. Тот же список, что решает
> маршрут данных (3.1), решает и выбор DNS-ответа. Не заводим отдельную эвристику
> «приватности» — только явно заданную маску. Это делает поведение предсказуемым
> и управляемым одним параметром.

#### 3.3.1. Транспорт исходящих DNS и адреса серверов

- **Транспорт:** оба пути шлют DNS **по TCP** (тот же формат с 2-байтовым
  префиксом длины), чтобы единообразно работать с тем, что прислал sing-box, и не
  зависеть от UDP-обрезки.
- **Внешний путь:** raw TCP-сокет → `bind_socket_to_interface(-I)` →
  `connect(<адрес назначения из SOCKS-запроса>, 53)`. То есть внешний DNS-сервер —
  это **тот адрес, на который sing-box открыл CONNECT** (`__DNS_SERVER__` из
  конфига контейнера, напр. `8.8.8.8`). Реле **ничего не хардкодит** и не берёт
  отдельный параметр — использует адрес из запроса, лишь принудительно направляя
  его через `-I`. upstream SOCKS для DNS не используется.
- **Дефолтный путь:** raw TCP-сокет **без** привязки к `-I` →
  `connect(<дефолтный DNS>, 53)`. Адрес дефолтного (внутреннего) DNS определяется
  **значением флага `--dns-split`** (см. §3.3.2) — это либо путь к resolv.conf-файлу
  (читаем первый `nameserver`), либо прямой адрес DNS-сервера. По умолчанию (флаг
  задан без значения) — системный `/etc/resolv.conf` хоста. Так «дефолтный путь»
  автоматически следует за состоянием VPN (когда AnyConnect поднят, он прописывает
  корп-резолвер `10.50.50.50` в resolv.conf), а корп-DNS-сервер достигается в обход
  `-I` (дефолтный путь по определению без `-I`).
  - **Когда читается источник (критично):** если источник — **файл**
    (resolv.conf), он читается **динамически — при каждом резолве дефолтного
    пути**, НЕ один раз при старте. Иначе поднятие AnyConnect (он перезаписывает
    resolv.conf в момент подъёма VPN) не будет замечено уже запущенным реле, и
    корп-имена уйдут на старый публичный DNS — основной сценарий сломается. Чтобы не
    дёргать файл на каждый DNS-запрос, допускается **микро-кэш** (mtime-based или
    TTL ~1–2 с). **Место микро-кэша:** модульный глобал (или атрибут
    `DnsSplitCache`) — гонка тут доброкачественна (в худшем случае двойное чтение
    файла, результат одинаков), отдельного `Lock` не требует. Если источник —
    **прямой адрес** DNS-сервера, он фиксирован (файл не читается).
  - **loopback-проверка применяется ТОЛЬКО к источнику-файлу.** Если источник-файл
    отсутствует, пуст, или первый `nameserver` — **loopback** (весь `127.0.0.0/8`
    — stub-резолверы `systemd-resolved` `127.0.0.53`, `dnsmasq` `127.0.0.1` и пр. —
    а также `::1`), дефолтный путь считается **недоступным** (эквивалент «не
    ответил» → берём внешний). **Прямой адрес** (`--dns-split 127.0.0.53`)
    loopback-проверке НЕ подвергается: реле на хосте, loopback-резолвер ему
    достижим и следует за VPN — пользователь задал его сознательно. При старте реле
    логирует предупреждение, если источник непригоден.

#### 3.3.2. Значение флага `--dns-split`

`--dns-split` — не просто вкл/выкл, а флаг с **необязательным значением**,
задающим источник дефолтного (внутреннего) DNS:

| Форма | Смысл |
|---|---|
| `--dns-split` (без значения) | включить; дефолтный DNS — из системного `/etc/resolv.conf` |
| `--dns-split /path/to/resolv.conf` | включить; читать первый `nameserver` из указанного файла (динамически, с микро-кэшем) |
| `--dns-split 10.50.50.50` | включить; дефолтный DNS — прямо этот адрес (файл не читается) |

**Порядок разбора значения (строго в этом порядке — иначе баг):**

0. **Источник значения.** Сначала определяем, задан ли режим вообще (§3.3):
   - CLI `--dns-split` присутствует → задан; его значение = аргумент, либо `''`
     (argparse `const=''`, флаг без аргумента);
   - иначе, если CLI не задан, берём env `DNS_SPLIT`; **пустая строка/не задано →
     режим выключен** (не идём дальше).
   CLI перекрывает env.
1. **Булево-подобное** (`1`,`true`,`yes`,`on`, регистронезависимо) **или пустая
   строка от CLI `const=''`** → включить, источник = системный `/etc/resolv.conf`.
   `0`,`false`,`no`,`off` → **выключено** (в т.ч. `--dns-split 0` поверх env).
2. Иначе пробуем `ipaddress.ip_address(value)` — если успех, это **прямой адрес**
   DNS-сервера.
3. Иначе — **путь к файлу** (resolv.conf-совместимый).

> Почему порядок важен: `ipaddress.ip_address('1')` бросает `ValueError`, а не даёт
> адрес. Если проверять IP **раньше** булева, значение `DNS_SPLIT=1` уйдёт в ветку
> «путь к файлу `1`» → попытка открыть несуществующий файл. Поэтому булевы значения
> отсекаются ПЕРВЫМИ.

Env-эквивалент — `DNS_SPLIT` с тем же значением, разбирается тем же порядком.
Внешний DNS-сервер этим флагом НЕ задаётся (он всегда берётся из SOCKS-запроса,
см. §3.3.1).

> Следствие: при выключенном VPN оба пути могут указывать на публичный DNS — это
> нормально (ответы совпадут, ∉ direct-net → берём внешний). Корп-имена в этот
> момент не резолвятся (сети физически нет) — ожидаемо.

### 3.4. Кэш

- TTL ~**2 минуты** (короткий: сеть/состояние VPN меняются). **TTL из DNS-ответа
  игнорируется намеренно** — фиксированный короткий TTL даёт быструю реакцию на
  переключение VPN, а не следование за (потенциально длинным) TTL записи.
- **Ключ:** имя запроса (`dns.name.Name` — сравнение регистронезависимо, поэтому
  ключуем именно объектом Name, а не строкой) + тип + класс (обычно IN).
- **Что именно кэшируется:** **не** сырой `response_wire`, а разобранный
  `dns.message` **объект** выбранного (внутреннего/внешнего) ответа. Причина —
  Query ID: у каждого запроса свой ID, и wire с чужим ID sing-box отбросит.
- **Сборка ответа клиенту (и на хите кэша, и на промахе)** — `build_wire`: под
  текущий запрос `resp = dns.message.make_response(current_query)` (ID из запроса
  автоматически), затем в `resp` копируются секции Answer/Authority/Additional и
  rcode из закэшированного `dns.message` (EDNS/OPT не копируем — в dnspython он
  живёт отдельно от additional; для нашей задачи не нужен); наружу `resp.to_wire()`
  с 2-байтовым префиксом длины.
- **SERVFAIL — политика кэширования (решено):** синтезированный SERVFAIL (оба
  пути молчат / таймаут семафора / исключение владельца) **НЕ кэшируется вообще**
  (не микро-TTL, а полное отсутствие в кэше). Иначе первый же двойной таймаут — а
  он наиболее вероятен ровно в момент переключения VPN — «убил» бы имя для повторов
  sing-box. При «не кэшируем вовсе» следующий повтор сразу пробует резолвить заново
  (и тест 22 детерминирован). SERVFAIL, реально **присланный DNS-сервером**, — тоже
  НЕ кэшируется (тот же принцип: ошибка резолва не должна залипать).
- **Ограничение роста `_entries`:** при записи под замком, если размер превысил
  порог (напр. 4096), удалять просроченные записи (`prune_expired`). Если после
  чистки всё ещё превышает порог (все записи живы) — допускается временное
  превышение; для домашней нагрузки нереалистично, но факт назван.
- **Тредобезопасность (важно):** реле — `ThreadingTCPServer` с
  `daemon_threads=True`, каждый клиент обрабатывается в отдельном потоке, и кэш —
  разделяемое состояние. Поэтому:
  - доступ к кэшу защищён `threading.Lock` (проверка/запись — под замком);
  - **дедупликация inflight-запросов:** пока запрос по ключу «в полёте», второй
    поток по тому же ключу не запускает свою пару DNS-запросов, а ждёт результат
    первого (паттерн `{key: threading.Event}`). Иначе N потоков на кэш-промахе
    породят N×2 параллельных DNS-запросов к одному имени.

### 3.5. Полный сценарий (обе фазы VPN)

**VPN поднят, запрос корпоративного имени `app.corp.example`:**
```
sing-box → реле: TCP :53 (DNS-запрос app.corp.example)
реле (dns-split): два запроса параллельно
   внешний путь (-I):   NXDOMAIN / публичный адрес
   дефолтный путь:      10.20.30.40  (корп-DNS через AnyConnect)
реле: 10.20.30.40 ∈ direct-net (10.0.0.0/8) → берём дефолтный → отдаём контейнеру
sing-box → реле: TCP :443 к 10.20.30.40
реле: 10.20.30.40 ∈ direct-net → прямой connect по таблице хоста → доходит ✓
```

**VPN поднят, запрос обычного имени `google.com`:**
```
реле (dns-split): два запроса параллельно
   внешний путь (-I):   142.250.x.x
   дефолтный путь:      142.250.x.x (или тайм-аут — неважно)
реле: ответ дефолтного НЕ ∈ direct-net → берём внешний → отдаём контейнеру
      обычный трафик к 142.250.x.x → НЕ ∈ direct-net → через upstream (внешний VPN) ✓
      (в корп-VPN не тащим)
```

**VPN выключен, любой запрос:**
```
реле (dns-split): два запроса параллельно
   внешний путь (-I):   отвечает (публичный DNS)
   дефолтный путь:      нет корп-сети → тайм-аут 2с ИЛИ публичный ответ
реле: ответ не ∈ direct-net → берём внешний → всё резолвится штатно ✓
      (никаких зависаний: мёртвый путь просто отваливается по таймауту)
```

## 4. Конфигурация

### 4.1. Принцип: env — основной способ, CLI перекрывает

Все параметры задаются переменными окружения (основной способ, используется в
`start.sh`). Любой параметр можно **переопределить** аргументом CLI — **аргумент
всегда главнее переменной окружения**. Это касается и существующих параметров, и
новых.

Правила разрешения:
- **Скаляры** (`BIND_INTERFACE`, флаг `DNS_SPLIT`): если задан CLI-аргумент —
  берётся он; иначе env; иначе дефолт.
- **Списки** (`DIRECT_NETS`): CLI **заменяет** env целиком (replace, не merge).
  Если заданы и `--direct-net`, и `DIRECT_NETS` — действует только CLI.
- **Пустые значения:** пустая строка в env (`DIRECT_NETS=`) трактуется как
  «не задано» (пустой список), а не как ошибка.
- **Существующее поведение:** `BIND_INTERFACE` сейчас читается **только** из CLI
  (`-I`). Добавление env-пути — новое поведение; оно не должно ломать текущий
  запуск через `-I` (CLI по-прежнему главнее).

### 4.2. Таблица параметров

| Назначение | Переменная окружения | Аргумент CLI (главнее) | Значение |
|---|---|---|---|
| Внешний интерфейс | `BIND_INTERFACE` | `-I` / `--interface` | имя (`en0`) или IP |
| Прямые сети | `DIRECT_NETS` | `--direct-net` (повторяемый) | CIDR через запятую, напр. `10.0.0.0/8` |
| Особый режим DNS | `DNS_SPLIT` | `--dns-split [ИСТОЧНИК]` | вкл + источник дефолтного DNS: пусто=системный resolv.conf, путь=файл, IP=адрес (см. §3.3.2) |
| (существующие) | `SERVER_USER`, `SERVER_PASSWORD`, `SOCKS5_SERVER`, `SOCKS5_USER`, `SOCKS5_PASSWORD`, `SOCKS5_UDP_BIND` | добавить одноимённые CLI | как раньше |

> Порядок разрешения каждого параметра в `main()`:
> `значение = CLI-аргумент if задан else os.environ.get(ENV) else дефолт`.
> Для повторяемого `--direct-net` / `DIRECT_NETS` — CLI-список **заменяет** env
> целиком (не мерж); пустой env = пустой список.

> Про адреса DNS-серверов: **отдельного параметра для внешнего DNS нет.** Внешний
> путь берёт адрес DNS-сервера **из самого SOCKS-запроса** (`__DNS_SERVER__`
> контейнера) и лишь направляет его через `-I`. Дефолтный путь берёт корп-DNS из
> `/etc/resolv.conf` хоста. Ни тот, ни другой не хардкодятся и не задаются флагом
> (см. §3.3.1).

### 4.3. `start.sh`

В `start.sh` задаём **переменные окружения** (не CLI-аргументы). Пример намерения
(точные значения — при реализации):
```
export BIND_INTERFACE=en0
export DIRECT_NETS=10.0.0.0/8
export DNS_SPLIT=1
```

### 4.4. Значение `__DNS_SERVER__` в конфиге контейнера

В `singbox-base.json` DNS-сервер имеет `server: __DNS_SERVER__` (шаблон,
подставляется в `mode-hostproxy.sh`). В режиме `--dns-split` реле **игнорирует**
этот адрес (смотрит только на порт 53), но sing-box всё равно требует **валидный
IP**. Поэтому при включённом dns-split в `__DNS_SERVER__` подставляется любой
корректный публичный IP (например `1.1.1.1`) — он служит лишь «адресом-заглушкой»,
на который sing-box откроет TCP:53 к реле. Фактический выбор DNS делает реле.

> **Предусловие: `__DNS_SERVER__` — всегда IPv4-литерал.** Текущий `handle_connect`
> реджектит ATYP=IPv6 (0x04) на входе (строка 353 реле: поддерживаются только IPv4
> и DOMAIN). Если подставить IPv6-адрес DNS, sing-box откроет CONNECT с ATYP=0x04 и
> реле ответит «не поддерживается» → DNS не заработает. Значит заглушка обязана быть
> IPv4 (`1.1.1.1`). Расширение приёма ATYP=IPv6 — вне рамок первой версии.

## 5. Архитектура кода

### 5.1. Разделение на модули

DNS-логика выносится в **отдельный файл** `../socks/dns_split.py`, лежащий рядом с
`socks-relay.py`. Реле импортирует его через
`sys.path.insert(0, dirname(__file__))` + `import dns_split` (проверено — приём
работает всегда, запуск из папки реле). Причина выноса — изоляция: DNS-парсинг и
логика выбора не должны загромождать основной SOCKS-код. **Решено: делаем отдельным
модулем** (пользователь одобрил изоляцию DNS-логики в отдельном файле).

**Импорт — условный, в `main()` после разбора аргументов, только если dns-split
включён.** Так `dnspython` становится предусловием лишь для этого режима, а не для
обычного запуска реле. Модуль `dns_split` держит `import dns.message` на своём
верхнем уровне; если библиотека отсутствует — `main()` ловит `ImportError` и
завершается с понятной ошибкой. (Тесты импортируют `dns_split` напрямую, где
`dnspython` установлен, — условность в `main()` им не мешает.)

### 5.2. `dns_split.py` (новый файл)

Отвечает только за DNS. Публичная функция примерно такого вида:

```
resolve_split(query_wire, external_iface, external_dns, direct_nets,
              timeout=2.0, cache=...) -> response_wire
```

`external_dns` здесь — адрес DNS-сервера **из SOCKS-запроса** (тот `__DNS_SERVER__`,
на который sing-box открыл CONNECT), а НЕ отдельный параметр конфигурации.
`handle_connect` передаёт его как `address` текущего соединения. Дефолтный DNS
определяется **источником из `--dns-split`** (§3.3.2): модуль либо читает
`nameserver` из файла (resolv.conf, динамически), либо использует переданный прямой
адрес. Источник передаётся в `resolve_split` (напр. параметром `default_dns_source`).

Внутри:
- разбор DNS-запроса и ответа через **`dnspython`** (см. ниже);
- два параллельных запроса (внешний путь: `external_dns` с привязкой к
  `external_iface`; дефолтный: DNS из источника `--dns-split` по таблице хоста);
- выбор по маске `direct_nets` (см. 3.3);
- кэш с TTL (см. 3.4).

#### Границы ответственности: кто читает сокет

Цикл чтения TCP-DNS (2-байтовый префикс длины → тело сообщения) остаётся **в
`handle_connect`** (у него есть `self.recvall()` — надёжное чтение ровно N байт,
строки 287–299 реле). В `dns_split.resolve_split()` передаётся уже **готовый
`query_wire`** (bytes одного DNS-сообщения), а обратно возвращается `response_wire`
(bytes). Модуль `dns_split` **не** трогает клиентский сокет — только исходящие
DNS-сокеты к серверам. Так модуль не зависит от внутренностей `SocksProxy`.

#### Структуры данных и жизненный цикл кэша (критично для потоков)

Реле — `ThreadingTCPServer`, а `SocksProxy` (`BaseRequestHandler`) **создаётся
заново на каждое соединение**. Поэтому кэш **не может** быть атрибутом хендлера —
он живёт **на объекте сервера** и разделяется всеми потоками:

- В `main()` создаётся единственный объект `DnsSplitCache` и присваивается
  атрибутом сервера: `server.dns_cache = DnsSplitCache(ttl=120)`.
- `handle_connect` обращается к нему через `self.server.dns_cache`.

`DnsSplitCache` инкапсулирует **и** данные, **и** синхронизацию. **В `_entries`
лежат разобранные `dns.message`-объекты (НЕ сырой wire)** — wire с чужим Query ID
sing-box отбросит, поэтому наружу ответ всегда пересобирается под текущий запрос
(см. §3.4):

```
class DnsSplitCache:
    _lock: threading.Lock
    _entries: dict[key -> (dns.message.Message, expiry)]   # разобранные ответы
    _inflight: dict[key -> threading.Event]                # запросы «в полёте»
```

Протокол одного резолва (ключ = qname+qtype+qclass; qname — `dns.name.Name`,
регистронезависимо). **Шаги 1–3 выполняются в ОДНОМ захвате `_lock`** — иначе между
проверкой `_entries` и записью `_inflight` возможна гонка двух владельцев:

```
with _lock:                              # ЕДИНЫЙ критический участок принятия решения
    hit = _entries.get(key)              # шаг 1
    if hit and not expired(hit):
        cached_msg = hit.message         # берём объект под замком
        # НЕ собираем wire под замком (make_response+copy+to_wire — CPU-работа,
        # сериализовала бы все хиты); build_wire — сразу после выхода из-под замка
        ev = None; owner = None          # это хит, дальше не идём
    else:
        cached_msg = None
        ev = _inflight.get(key)          # шаг 2
        if ev is None:                   # шаг 3: мы — владелец
            ev = threading.Event()
            _inflight[key] = ev
            owner = True
        else:
            owner = False
# замок отпущен
if cached_msg is not None:               # хит: собираем wire ВНЕ замка
    return build_wire(cached_msg, current_query)
```

- **Если мы владелец:**
  - захватываем `BoundedSemaphore` **с таймаутом** — `acquire(timeout=REQUEST_TIMEOUT)`
    (только владелец, не ждущие). Если слот не получен за таймаут → `chosen_msg` =
    синтезированный SERVFAIL (не виснем неограниченно при всплеске уникальных имён);
  - **весь резолв обёрнут в `try/except`**: пара DNS-запросов (см. ниже), выбранный
    `dns.message` → `chosen_msg` (при раннем выходе — тоже; см. §«Механизм
    параллелизма» — ровно один путь присвоения). **Любое исключение** внутри →
    `chosen_msg = servfail(current_query)` (не даём исключению улететь наружу и
    убить соединение — `handle()` ловит только `ConnectionInterrupted`);
  - в `finally` (всегда): освободить семафор (если был захвачен); `with _lock:` —
    **кэшировать `chosen_msg` в `_entries` ТОЛЬКО если это НЕ SERVFAIL**
    (синтезированный ИЛИ присланный сервером — оба не кэшируем, §3.4); удалить ключ
    из `_inflight`, `ev.set()`;
  - вернуть `build_wire(chosen_msg, current_query)` (вне замка).
- **Если мы ждущий:** `ev.wait(timeout=WAIT)` (`WAIT = 2*REQUEST_TIMEOUT + 1 = 5с`;
  семафор ждущий НЕ захватывает). После пробуждения `with _lock:` прочитать
  `_entries[key]` в локальную переменную (объект), **замок отпустить**, затем
  `build_wire(...)` **вне замка**; если записи нет (владелец не закэшировал —
  SERVFAIL/ошибка) → синтезированный SERVFAIL под текущий запрос. `wait` **всегда**
  с таймаутом — вечного ожидания нет.
  > Тайминги сходятся: `acquire(timeout=2с)` + дедлайн 2с ⇒ владелец завершается за
  > ≤ ~4с < WAIT=5с. Ждущий, проснувшийся раньше владельца (редко), получит
  > SERVFAIL — приемлемо; deadlock отсутствует (семафор освобождается, `set()`
  > безусловен).

Итог: на кэш-промахе по одному имени — **ровно одна** пара исходящих DNS-запросов;
ответ всегда пересобирается под Query ID текущего запроса; синтезированный SERVFAIL
не залипает в кэше; ошибка владельца не приводит к deadlock.

#### Механизм параллелизма и точный алгоритм ожидания

Два запроса запускаются в **двух `threading.Thread`** (внешний / дефолтный), каждый
кладёт `(tag, dns.message | None)` в общую `queue.Queue`. Владелец собирает
результаты по **общему дедлайну** `deadline = monotonic() + REQUEST_TIMEOUT`
(REQUEST_TIMEOUT = 2с, честный end-to-end).

**Заведомо недоступный дефолтный путь.** Если источник дефолтного DNS непригоден
(loopback/пустой resolv.conf — §3.3.1), дефолтный поток **не запускается**, а его
результат сразу считается «пришёл, пустой» (`default_done=True, default_resp=None`).
Иначе внешний ответ ждал бы дефолтный до полного дедлайна — +2с на **каждый** промах
кэша на systemd-resolved-хостах.

**Точный алгоритм** (единственный путь выхода — присвоение `chosen_msg` и `break`;
голого `return` в цикле нет, чтобы `finally` владельца всегда отработал кэш/inflight):

```
chosen_msg = None
default_done = external_done = False
default_resp = external_resp = None
if default_source_unusable:          # loopback/пусто — поток не стартуем
    default_done = True
while not (default_done and external_done):
    remaining = deadline - monotonic()
    if remaining <= 0:
        break
    try:
        tag, resp = queue.get(timeout=max(0, remaining))   # max(0,...) от гонки
    except Empty:
        break
    if tag == 'default':
        default_done, default_resp = True, resp
        # РАННИЙ ВЫХОД: дефолтный дал адрес ∈ direct_nets → корп-имя, внешний неважен
        if resp is not None and has_addr_in(resp, direct_nets):
            chosen_msg = default_resp
            break
    else:  # 'external'
        external_done, external_resp = True, resp
        # внешний НЕ даёт раннего выхода, НО если дефолтный уже недоступен/пуст —
        # ждать больше нечего, решаем сразу:
        if default_done:
            break

# финальное решение по маске (если ранний выход не сработал):
if chosen_msg is None:
    if default_resp is not None and has_addr_in(default_resp, direct_nets):
        chosen_msg = default_resp            # корп-имя
    elif external_resp is not None:
        chosen_msg = external_resp           # внешний приоритетен для не-корп
    elif default_resp is not None:
        chosen_msg = default_resp            # ответил только дефолтный
    else:
        chosen_msg = servfail(current_query) # оба молчат (синтезированный — не кэшируем)
# chosen_msg → в finally владельца (см. выше): кэш + build_wire
```

Ключевое: недоступный дефолт помечается `default_done` сразу → приход внешнего
завершает резолв **немедленно** (нет стойла 2с); `max(0, remaining)` исключает
`ValueError`; выход только через `chosen_msg`+`break`, а не `return` — `finally`
владельца всегда отрабатывает.

Пояснение к таблице §3.3: «ответил только один → берём его» реализуется тем, что
при `Empty`/дедлайне цикл выходит, и в финальном блоке выбирается тот единственный,
что не `None`. «Оба ответили, дефолтный ∈ маска → дефолтный» — ловится ранним
выходом (или страховкой в финале). Внешний **никогда** не даёт раннего выхода —
всегда оставляем шанс дефолтному прийти с корп-адресом до дедлайна.

**Про `settimeout`:** `sock.settimeout(t)` — таймаут на **каждую** операцию
(connect ≤ t, затем recv ≤ t, до `2t` на путь). Но владелец ограничен **общим**
`deadline` в `queue.get`, а не суммой пер-операционных таймаутов, поэтому end-to-end
латентность резолва ≤ REQUEST_TIMEOUT. `WAIT` для ждущих = `2*REQUEST_TIMEOUT + 1`
(= 5с), считается от их момента `wait` — с запасом над наихудшим дедлайном владельца.

**Предохранитель от thread explosion:** пара DNS-потоков поднимается под
`threading.BoundedSemaphore(MAX_INFLIGHT_RESOLVES)` (напр. 32). Захватывает семафор
**только владелец** резолва (после того как под `_lock` определён owner) — **ждущие
семафор НЕ трогают** (иначе они заняли бы слоты, не делая работы, и предохранитель
сломался бы). Так ограничивается число одновременных реальных резолвов, не меняя
логику: при всплеске лишние владельцы ждут слота. Дедупликация inflight (один резолв
на имя) уже гасит повторы; семафор гасит всплеск уникальных имён.

#### Управление исходящими DNS-сокетами (без утечек fd)

- Каждый исходящий сокет: `settimeout(REQUEST_TIMEOUT)` **до** `connect`; выбор
  `AF_INET`/`AF_INET6` по типу адреса DNS-сервера; закрытие в `try/finally`
  **независимо** от исхода. Внешний путь по предусловию §4.4 (`__DNS_SERVER__`
  всегда IPv4) — всегда `AF_INET`; дефолтный — по типу адреса из источника.
- **Worker-поток ловит ЛЮБЫЕ исключения.** Тело каждого потока (внешнего/дефолтного)
  обёрнуто в `try/except Exception` → в очередь всегда кладётся `(tag, msg | None)`,
  где `None` при таймауте/ошибке/`bind_socket_to_interface`→`ConnectionInterrupted`
  (строка 199 реле). Иначе исключение в потоке молча пропало бы, очередь не
  получила результата, и владелец досидел бы до полного дедлайна вместо мгновенного
  «путь ответил ничем».
- **Проигравший поток НЕ прерывается извне.** Мы не полагаемся на то, что
  `close()` из чужого потока прервёт его `recv` (на практике это не гарантировано,
  а fd может быть переиспользован ОС). Вместо этого: проигравший поток доживает до
  своего собственного `settimeout`, затем закрывает свой сокет в `finally` и
  завершается. Он **ничего не пишет** в кэш и никак не влияет на уже принятое
  владельцем решение (его запоздалый результат просто игнорируется — очередь уже
  не читается). Максимальная «переживалка» проигравшего — до **трёх**
  per-operation таймаутов (connect + recv префикса + recv тела ≈ до ~6с при
  наихудшей сети), обычно много меньше; потоки daemon, утечки нет.

#### Парсинг DNS: `dnspython` (принятое решение)

DNS-ответ может содержать **CNAME-цепочки**, **сжатие имён** (compression-
указатели, RFC 1035) и **несколько A/AAAA-записей**. Разбирать это вручную на
`struct` — фактически написать полноценный DNS-парсер: хрупко, много кода, много
краевых случаев. Поэтому используем библиотеку **`dnspython`**.

- Вес: ~331 КБ, **чистый Python** (`py3-none-any`, без C-расширений и без
  транзитивных зависимостей). Ставится одной командой `pip install dnspython`.
- Что даёт из коробки: `dns.message.from_wire()` / `to_wire()` разбирают и
  собирают DNS-сообщения (compression, любые типы записей) без ручного парсинга.
  **Уточнение про CNAME:** `from_wire()` не «разрешает» CNAME в сеть — оно лишь
  парсит сообщение. Стандартный ответ содержит CNAME **и** конечные A/AAAA в одной
  секции Answer. Поэтому адреса извлекаем итерацией по `msg.answer`, собирая **все**
  rrset с `rdtype in (A, AAAA)` — независимо от наличия CNAME. Отдельно «ходить по
  цепочке» не нужно: конечные A-записи уже лежат в Answer.
- Установка на хосте — предусловие запуска реле в режиме `--dns-split`. Если
  библиотека отсутствует, а `--dns-split` включён — реле завершается с понятной
  ошибкой (не деградирует молча).

#### Извлечение адресов и правило маски (multi-A)

Из ответа берём **все** A/AAAA-адреса из секции Answer (итерация по `msg.answer`,
`rdtype in (A, AAAA)`). Правило маски — **ANY**:

- `direct_nets` — `list[ipaddress.IPv4Network | ipaddress.IPv6Network]`,
  распарсенный **при старте** из строк через `ipaddress.ip_network(s, strict=False)`
  (невалидный CIDR → ошибка старта, не молча). Проверка адреса:
  `ipaddress.ip_address(a) in net`.
  - **Осторожно (crash-bug):** `ip_address('fd00::1') in ip_network('10.0.0.0/8')`
    в Python бросает **`TypeError`** (разные семейства), а не возвращает False.
    Поэтому `has_addr_in` обязана **пропускать** проверку при несовпадении семейств:
    сравнивать IPv4-адрес только с IPv4-сетями, IPv6 — только с IPv6. Иначе любой
    AAAA-ответ при IPv4-маске (`10.0.0.0/8`) уронит поток. Практика: проверять
    `addr.version == net.version` перед `in`.
- если **хотя бы один** адрес из ответа дефолтного пути ∈ `direct_nets` → ответ
  считается «внутренним» (§3.3), возвращаем ответ **дефолтного** пути целиком (как
  есть, без фильтрации записей);
- иначе → «внешний».

Причина ANY (а не ALL): корпоративное имя, зарезолвленное корп-DNS, вернёт хотя бы
один `10.x`; смешанные ответы (часть внутренних, часть внешних) трактуются как
внутренние, потому что доступ к сервису идёт по внутреннему адресу.

#### Что считается «ответил»

«Путь ответил» = **пришёл любой валидный DNS-ответ**, включая `NXDOMAIN`,
`SERVFAIL`, `REFUSED` и ответы без A/AAAA-записей. Ответ без адресов трактуется как
«∉ direct-net» → при равенстве обоих ведёт к выбору внешнего (см. таблицу §3.3).

#### Не-адресные типы запросов (PTR, MX, TXT, SRV, …)

В ответе таких типов нет A/AAAA для проверки маски. Правило: **не-адресный ответ
трактуется как «∉ direct-net»** → по таблице §3.3 при наличии внешнего берётся
внешний. Уточнение: «всегда внешний» — не абсолют: если внешний путь молчит, а
не-адресный ответ пришёл только от дефолтного, срабатывает ветка «ответил только
один» → вернётся дефолтный. Ограничение:
обратные PTR-запросы для `10.x` в первой версии пойдут на внешний DNS и, скорее
всего, не разрезолвятся. Это осознанное упрощение (см. §7).

### 5.3. Точечная врезка в `socks-relay.py`

Существующая логика **не меняется**. Ключевой момент: развилки ставятся в
`handle_connect(address, port)` **до** создания upstream-сокета (до блока
`with socket_class() as remote:`, строки ~399–432), чтобы для DNS-пути и
direct-net-пути не создавался лишний сокет.

На входе `handle_connect` `address` — это то, что пришло в SOCKS-запросе. sing-box
шлёт DNS как CONNECT на **IP-литерал** (`<dns_server_ip>:53`, ATYP=0x01), и
корпоративные сервисы после резолва — тоже на IP. Поэтому в типовом потоке `address`
уже IP, и проверки `port==53` / принадлежности `direct_nets` работают напрямую.
Если пришло доменное имя (ATYP=DOMAIN) и рассматривается direct-net-ветка — для
проверки маски пришлось бы `getaddrinfo(address)` на хосте. Это делаем **только
если `direct_nets` непусты** (иначе ветка direct-net не активна — не тратим резолв).
Ограничение (называем честно): при поднятом VPN такой `getaddrinfo` уйдёт в
корп-резолвер для **любого** доменного CONNECT — это ровно та утечка, что отвергнута
в §2.2, поэтому она допустима лишь как узкий крайний случай. **В нашем
hostproxy-потоке доменов не бывает** (`sniff` без `override_destination` —
`singbox-base.json:38–44` — sing-box отдаёт реле IP, не имя), так что на практике
ветка не срабатывает. Резолв блокирующий — с `getaddrinfo` без своего таймаута;
если это станет проблемой, вынести за отдельный флаг. **Family-guard (важно):**
`getaddrinfo` может вернуть IPv6, а `direct_nets` — только IPv4 → та же ловушка
`TypeError` при `in`, что и в `has_addr_in` (§5.2). Поэтому проверку принадлежности
делать через тот же family-safe `has_addr_in` (скип при несовпадении версий), либо
фильтровать `getaddrinfo(..., family=AF_INET)`.

Развилки (в порядке проверки):

1. **DNS-split:** если `dns_split` включён, **`-I` задан** (см. §3.3 предусловие),
   `port == DNS_PORT` (`DNS_PORT = 53` — модульная константа, она же точка
   подстановки в юнит-тестах §6) **и** `address` — **IP-литерал** (не ATYP=DOMAIN):
   - отправить клиенту SOCKS-reply успех: `self._pack_reply(0x00, '0.0.0.0', 0)`
     (BND-адрес фиктивный — реального upstream-сокета в DNS-пути нет);
   - войти в цикл I/O по TCP (RFC 7766). **Разграничение чистого EOF от обрыва в
     середине (3 шага):** (а) в начале итерации `d = recv(1)` (один байт префикса);
     если `d == b''` → **клиент закрыл соединение между сообщениями → нормальный
     выход из цикла без логирования**; (б) иначе `recvall(1)` дочитывает второй
     байт префикса, `recvall(msg_len)` — тело; (в) обрыв на шаге (б) → существующий
     `ConnectionInterrupted` (это действительно аномалия). Затем вызывается
     `dns_split.resolve_split(query_wire, external_dns=address, ...,
     cache=self.server.dns_cache)`, ответ пишется с 2-байтовым префиксом; повторять
     (pipelining/keep-alive — **последовательный** request→response, без
     параллелизма в пределах одного соединения);
   - **ранний `return`** — до создания `remote`-сокета и без вызова
     `exchange_loop`.
2. **direct-net:** иначе, если IP-цель ∈ `direct_nets`:
   - открыть **прямой** сокет к цели **без** upstream и **без** `-I`
     (по таблице хоста): `socket.socket(AF_INET|AF_INET6 по типу адреса)`,
     `settimeout(DIRECT_CONNECT_TIMEOUT)` (новая константа, напр. 10с; НЕ оставлять
     `None`) перед `connect`, затем обычный `exchange_loop`. Это отдельная ветка
     создания `remote` (голый `socket.socket`, не `socks.socksocket`).
3. **иначе** — существующий chained-путь без изменений (upstream + `-I`).

Что **не** затрагивается: UDP-путь (`handle_udp_associate` и его relay-функции),
логика аутентификации, `bind_socket_to_interface`, `exchange_loop`. DNS-split и
direct-net живут только в TCP-CONNECT-ветке.

Разбор новых env/CLI — в `main()` рядом с существующим `-I`.

**Паттерн хранения новых параметров (зафиксировано).** `DIRECT_NETS`, флаг
`DNS_SPLIT` и его значение (источник дефолтного DNS — путь-к-файлу или IP) хранятся
в **модульных глобалах** (как уже сделано для `BIND_INTERFACE`), устанавливаются
один раз в `main()` после разбора аргументов.
Причина: `SocksProxy.setup()` вызывается на **каждое** соединение (строки 262–275),
и читать/парсить эти параметры там — расточительно и рассогласованно. Исключение —
**кэш** (`DnsSplitCache`): он хранит изменяемое разделяемое состояние и живёт на
**объекте сервера** (`self.server.dns_cache`), а не в глобале. То есть: неизменяемая
конфигурация → глобалы; разделяемое изменяемое состояние → атрибут сервера.

**CLI-переопределение существующих параметров.** `setup()` сейчас читает
`SERVER_USER`/`SOCKS5_SERVER`/… из `os.environ` на каждое соединение (строки
262–275). Чтобы CLI-аргумент был главнее env без переписывания `setup()`, разрешение
CLI>env для этих параметров делается **один раз в `main()`**, и если CLI задан —
соответствующая переменная **проставляется в `os.environ` строго ДО
`serve_forever()`** (`os.environ['SERVER_USER'] = args.server_user`). Тогда
существующий `setup()` продолжает читать env, но уже с учётом CLI. (Альтернатива —
глобалы, но правка `setup()` шире; выбираем инъекцию в env как наименее инвазивную.)

> Секреты в argv: `--server-password`/`--socks5-password` в командной строке видны в
> `ps` на общем хосте. **Env остаётся рекомендуемым способом для паролей**; CLI для
> них — только как перекрытие при отладке.

**Вынести разрешение параметров из `main()` (для тестируемости).** Сейчас `main()`
(строки 939–1001) сразу уходит в `serve_forever()`. Разбор+разрешение
env/CLI вынести в отдельную функцию (напр. `resolve_config(argv, environ)`),
которую тест 11 (CLI>env) вызывает **без** запуска сервера. `main()` вызывает её и
затем `serve_forever()`.

**argparse для `--dns-split` (`nargs='?'`).** Флаг объявляется как
`add_argument('--dns-split', nargs='?', const='', default=None)`:
- отсутствует → `default=None` → режим выключен;
- `--dns-split` без значения → `const=''` → включён, источник = системный
  resolv.conf;
- `--dns-split ЗНАЧЕНИЕ` → значение (булево/IP/путь, разбор по §3.3.2).
Ловушка поглощения позиционного: `--dns-split '*:1080'` съест listen-адрес как
значение флага. Поэтому в документации/`start.sh` использовать форму
`--dns-split=ЗНАЧЕНИЕ` (через `=`), либо ставить флаг после позиционного listen.

В докстринг/шапку файла добавить **явное** описание маршрутизации, особенно

## 6. Тесты (`test_socks_relay.py`)

**Подход к изоляции от сети.** Ядро логики (`resolve_split`, выбор по маске,
кэш, дедупликация) тестируется **юнит-уровнем** — точка мокирования — функция
отправки одного DNS-запроса (напр. `dns_split._query_one(server, iface, wire,
timeout)`), которую тесты подменяют на заглушку, возвращающую заранее собранный
через `dnspython` `response_wire` (или бросающую timeout). Так не нужен реальный
DNS и порт 53. Тесты дедупликации подменяют ту же функцию счётчиком вызовов под
`Lock`. Интеграционные ветки (`direct-net`, «флаг выключен») тестируются через
локальный фиктивный TCP-слушатель на произвольном порту (как в существующих
тестах). Модульная константа `DNS_PORT` (=53) в юнит-тестах переопределяется на
тестовый порт, а не байндится реальный 53 (не требует root).

Добавить, не ломая существующие 9 тестов:

1. **DNS-split, внутренний ответ:** дефолтный путь вернул адрес ∈ `direct-net` →
   реле возвращает его (не внешний). Заодно проверить, что **внешний путь
   обратился к адресу из SOCKS-запроса** (анти-регрессия: адрес не хардкодится).
2. **DNS-split, внешний ответ:** дефолтный путь вернул адрес ∉ `direct-net` →
   реле возвращает внешний.
3a. **Молчит внешний:** внешний не ответил до дедлайна, дефолтный ответил → берём
   дефолтный.
3b. **Молчит дефолтный:** дефолтный не ответил до дедлайна, внешний ответил → берём
   внешний.
4. **Оба молчат:** → SERVFAIL с тем же Query ID, что в запросе.
5. **Ранний выход:** дефолтный ∈ direct-net приходит раньше внешнего → решение
   принимается сразу, ответа внешнего не ждём (проверка, что внешний не влияет).
6. **Кэш:** повторный запрос в пределах TTL не инициирует новую пару DNS-запросов;
   отданный ответ несёт Query ID нового запроса, а не закэшированного.
7. **Кэш, дедупликация inflight:** N одновременных потоков по одному ключу
   порождают ровно одну пару исходящих DNS-запросов (проверка `Lock` + `Event`).
8. **Дедупликация при падении владельца:** если поток-владелец бросил исключение,
   ожидающие потоки не зависают (получают SERVFAIL), `_inflight` очищается.
9. **Pipelining:** два DNS-запроса подряд по ОДНОМУ TCP-соединению, с **разными
   Query ID** — оба получают корректные ответы, каждый со СВОИМ Query ID; чистый
   EOF после второго не логируется как ошибка.
10. **direct-net bypass:** соединение к IP ∈ `direct-net` идёт прямым connect (не
    через upstream).
11. **Приоритет CLI > env:** для `-I`, `DIRECT_NETS`, `DNS_SPLIT` аргумент
    перекрывает env; `DIRECT_NETS=` (пусто) = пустой список; `DNS_SPLIT=0` =
    выключено. Проверяется через выделенную `resolve_config(argv, environ)` (без
    запуска сервера).
12. **Флаг выключен:** при `dns_split=off` соединение на порт 53 идёт обычным путём
    (регрессия: логика не изменилась).
13. **CNAME-цепочка:** ответ `name→CNAME→A(10.x)` — реле извлекает `10.x` через
    dnspython (итерация Answer) и относит к внутреннему.
14. **Несколько A-записей (ANY):** ответ `[10.x, 8.8.8.8]` → внутренний (хотя бы
    один в маске).
15. **Не-адресный тип (PTR/MX):** ответ без A/AAAA → трактуется как внешний.
16. **resolv.conf = loopback:** первый `nameserver 127.0.0.53` → дефолтный путь
    недоступен → берётся внешний.
17. **Источник/включение `--dns-split`:** значение-IP (`--dns-split 10.50.50.50`) →
    дефолтный путь шлёт на этот адрес (файл не читается); значение-путь → читается
    `nameserver` из файла; флаг без значения (CLI `const=''`) → системный
    `/etc/resolv.conf`; `DNS_SPLIT=1` (env) → системный resolv.conf (НЕ путь к файлу
    `1`); **`DNS_SPLIT=""` (env, пусто) → выключено**; **`--dns-split 0` (CLI) →
    выключено** (в т.ч. поверх `DNS_SPLIT=1`).
18. **Без `-I` split не активен:** при `dns_split` включённом, но `-I` не заданном,
    соединение на порт 53 идёт существующим путём реле (в chained-режиме — через
    upstream) — развилки нет.
19. **AAAA при IPv4-маске не крашит:** дефолтный вернул AAAA, `direct_nets` только
    IPv4 → `has_addr_in` не бросает `TypeError`, адрес трактуется как не-в-маске.
20. **Динамика resolv.conf:** источник-файл меняет `nameserver` между двумя
    резолвами (эмуляция подъёма AnyConnect) → второй резолв идёт уже на новый
    адрес (проверка перечитывания, не «прочитал при старте»).
21. **Истечение TTL:** запись, ставшая старше TTL, не отдаётся из кэша —
    инициируется новый резолв.
22. **SERVFAIL не залипает:** синтезированный SERVFAIL (оба молчат) **не
    кэшируется вовсе** — немедленно следующий запрос по имени снова резолвит (не
    отдаёт закэшированный SERVFAIL).
23. **Семафор — только владелец:** при > `MAX_INFLIGHT_RESOLVES` одновременных
    резолвов ждущие по своим ключам не занимают слоты семафора (проверка, что
    предохранитель ограничивает именно владельцев).
24. **Недоступный дефолт не тормозит:** источник-loopback + внешний ответил быстро
    → резолв завершается сразу по внешнему, без стойла до дедлайна 2с.
25. **Обрыв посреди DNS-сообщения:** соединение рвётся между байтами префикса/тела
    (шаг «б» 3-шагового EOF) → `ConnectionInterrupted` (аномалия), НЕ спутано с
    чистым EOF между сообщениями.
26. **Семафор-таймаут → SERVFAIL:** владелец не получил слот за `acquire(timeout)`
    → возвращает SERVFAIL, который НЕ кэшируется (следующий запрос резолвит заново).
27. **prune_expired:** при превышении порога `_entries` просроченные записи
    удаляются под замком при следующей записи.
28. **Прямой loopback-адрес допустим:** `--dns-split 127.0.0.53` НЕ трактуется как
    «недоступный» (loopback-проверка — только для источника-файла); дефолтный путь
    шлёт на этот адрес.
29. **SERVFAIL от сервера не кэшируется:** дефолтный/внешний сервер прислал
    настоящий SERVFAIL → он отдаётся клиенту, но в кэш НЕ кладётся (следующий запрос
    резолвит заново).
30. **Unparseable/≠1 question → закрытие:** обрезанный запрос или запрос с 0/2
    question-секциями → соединение закрывается, без краша обработчика.
31. **rcode копируется:** закэшированный NXDOMAIN на кэш-хите отдаётся как NXDOMAIN
    (а не NOERROR от голого `make_response`).
32. **DOMAIN на порт 53 → обычный путь:** CONNECT с ATYP=DOMAIN на порт 53 при
    активном dns-split НЕ уходит в DNS-развилку, идёт существующим путём.
33. **Исключение владельца → SERVFAIL, соединение живо:** если резолв бросил
    исключение, владелец возвращает клиенту SERVFAIL (не рвёт соединение), ждущие
    получают SERVFAIL, `_inflight` очищен.

Тесты гоняются **на хосте** (в контейнере нет нужного окружения реле;
`dnspython` ставится на хосте).

## 7. Открытые вопросы / ограничения (названы честно)

1. **Зависимость `dnspython`** — предусловие для `--dns-split` (ставится на хосте,
   ~331 КБ, чистый Python). Без неё при включённом флаге реле не стартует с
   понятной ошибкой.
2. **Адрес дефолтного DNS из `/etc/resolv.conf`.** «Дефолтный путь» шлёт запрос на
   DNS-сервер(ы) из системного `/etc/resolv.conf` хоста. Это работает, потому что
   AnyConnect при подключении прописывает туда корп-DNS. Ограничение: если хост
   настроен нестандартно (DNS через `systemd-resolved` на `127.0.0.53`, без записи
   реального сервера в resolv.conf) — реле может не увидеть корп-DNS. Проверить на
   конкретном хосте при реализации.
3. **PTR / не-адресные типы** идут на внешний путь → обратный DNS для `10.x` в
   первой версии не резолвится (публичный DNS вернёт NXDOMAIN на `*.in-addr.arpa`
   для приватных адресов — клиент это переживает штатно). Если понадобится —
   добавить маршрутизацию по ВОПРОСУ (qname `*.in-addr.arpa` для 10.x → дефолтный
   путь).
4. **Без `-I` DNS-split не активен.** Развилка включается только при заданном `-I`
   (см. §3.3). Если `-I` не задан, `--dns-split` — no-op (реле логирует при старте),
   DNS идёт существующим путём реле (в chained-режиме — через upstream). Так
   исключён DNS-leak/бессмыслица «оба пути через одну таблицу».
5. **TCP-DNS с 2-байтовым префиксом** (RFC 7766), включая несколько запросов на
   соединении — покрыто циклом I/O (§5.3) и тестами.
6. **IPv6/AAAA:** маска `--direct-net` в первой версии — IPv4 (`10.0.0.0/8`). Если
   корпоративных IPv6-подсетей нет, AAAA-ответы всегда «внешние». Добавить
   IPv6-CIDR при необходимости.
7. **direct-net в chained-режиме** = реле само делает прямой connect (не через
   upstream). Опирается на то, что таблица хоста доведёт `10/8` до корп-сети (через
   AnyConnect).
8. **Только порт 53 / только TCP-DNS:** DoH/DoT в контейнере не появятся, т.к.
   конфиг sing-box шлёт DNS исключительно по TCP:53 (конфиг наш).
9. **UDP-DNS:** если DNS-сервер в конфиге сменится на `type:udp`, распознавание по
   порту 53 в UDP-пути (`_udp_relay_direct`, там уже есть `dst_port`) надо будет
   покрыть. В первой версии — только TCP.
10. **Нет пула исходящих DNS-соединений.** Каждый кэш-промах открывает до двух
    новых TCP-соединений к DNS-серверам. Кэш (~2 мин) сглаживает всплески
    (повторные имена не резолвятся заново), но при большом потоке уникальных имён
    это лавина коротких TCP-соединений. Смягчено `BoundedSemaphore` (§5.2) на число
    одновременных резолвов. Для первой версии приемлемо; при необходимости — пул
    keep-alive соединений (RFC 7766 их допускает).
11. **«Зомби»-потоки проигравшего пути.** После того как владелец ответил, поток
    проигравшего пути живёт ещё до своих per-operation таймаутов (до ~6с в наихудшем
    случае: connect+recv+recv, обычно меньше), затем сам закрывается. При потоке
    кэш-промахов это некоторое число фоновых daemon-потоков в ожидании — не течёт
    (все завершаются), но стоит знать. `BoundedSemaphore` косвенно ограничивает и их
    число.
12. **Латентность промаха = медленнейший из активных путей.** Внешний путь никогда
    не даёт раннего выхода (§5.2), поэтому если дефолтный DNS **числится** в
    resolv.conf, но не отвечает (SYN drop — типично в момент разрыва AnyConnect,
    когда адрес ещё в файле, а сети уже нет), каждый **уникальный** промах кэша
    стоит полные 2с (дедлайн). Loopback-шорткат покрывает только stub-случай, не
    «мёртвый, но прописанный». Кэш (~2 мин) сглаживает повторы. Это самый заметный
    пользователю режим деградации; при необходимости — снизить `REQUEST_TIMEOUT`
    или добавить более быстрый health-check дефолтного пути.

## 8. Порядок работ

1. `dns_split.py` — парсинг + выбор по маске + кэш (ядро, наибольший риск).
2. Врезка `--direct-net` в `socks-relay.py` (прямой connect в обход upstream/`-I`).
3. Врезка DNS-split в `handle_connect` (порт 53 → делегирование).
4. Конфиг env/CLI (приоритет CLI > env) + `start.sh`.
5. Документация в шапке `socks-relay.py`.
6. Тесты.
7. Независимое код-ревью → правки.
